00
The whole picture
Every night the server packs everything it needs, locks the archive with a passphrase and sends it out. If the server dies, you rent a new one and restore from any copy.
Three copies in three places. Google can lock an account, a laptop can be stolen, a disk can fail. If one copy is lost, two remain.
The passphrase never travels with the archive. It isn’t inside the archive, in logs or in Telegram. Without it nobody can open a copy, including you.
A backup you never restored is not a backup. Test the restore once right after setup, then once a month.
01
What goes into the archive
This is the setup that runs every night on the instructor’s server. The prompt in section 03 builds the same on yours.
PartHow it’s copied
DatabasesDumps, never raw files: Postgres with all roles, every SQLite file as a hot copy while it runs
Agent and keys~/.openclaw, project folders, .env files, ~/.ssh, the Google sign-in
SystemSSH, firewall and service settings, plus a list of versions and installed plugins
Left outThings that reinstall by themselves: node_modules, .venv, caches, logs, OpenClaw plugins. Their list goes in the archive
Lessons from a live server:
• A systemd timer starts the job, not cron: on Debian cron ignored the time zone and ran an hour off.
• A Google service account can’t upload to a personal Drive: it has no storage and gets error 403. Use your own Google sign-in.
• Before uploading, the script opens the archive with the passphrase as a test.
• Old copies are deleted only after the new one is confirmed on Drive.
• A watchdog writes to Telegram if there was no successful backup for 26 hours.

Copy 1: Google Drive every night
You need Google Workspace MCP on the server first: the backup uploads with the same Google sign-in. See the handout Google Workspace MCP. Prompt A · nightly backup to Google Drive
Set up a nightly encrypted backup of my whole server to my Google Drive. Work in three passes: look around, show me a plan and wait for my OK, then install. Delete or overwrite nothing without my "yes". For anything about OpenClaw use the openclaw-docs skill. Never print secrets in the chat. Goal: every night the server dumps the databases, packs everything, encrypts it, uploads it to Google Drive, keeps the last 7 archives and messages me in Telegram. If a step fails, the message says which one. 1. Recon, change nothing: ssh to my server. List Docker containers and databases (if any), SQLite files, project folders in /root, /opt, /home, and free disk space. 2. Plan: what goes in, what is excluded, approximate size, start time. Wait for my OK. 3. Archive contents: - all Postgres/MySQL databases if present (for Postgres: pg_dumpall plus --roles-only); - every SQLite file as a hot copy through Python's sqlite3 backup API (the sqlite3 CLI may be missing); - ~/.openclaw, project folders, .env files, ~/.ssh, ~/.google_workspace_mcp; - system config (sshd, ufw, fail2ban, systemd units, cron) and a manifest: openclaw --version, plugin list, docker ps -a, images; - exclude: node_modules, .venv, __pycache__, caches, logs, Codex log databases (logs_*.sqlite), codex-home/cache, ~/.openclaw/npm (list it in the manifest), old backup folders. 4. Encryption: gpg --symmetric --cipher-algo AES256, passphrase read from /root/.backup-passphrase (mode 600). Tell me when to create it; I keep it in Google Password Manager. It never goes into the archive, logs or Telegram. Warn me that without it nothing can be restored. 5. Google Drive through rclone with MY Google account. No service account: it has zero storage quota and uploads fail with 403. Google Workspace MCP is already signed in on this server: build the rclone remote from its OAuth client and token in ~/.google_workspace_mcp, but only if the token's scopes include full Drive access. Otherwise run rclone authorize "drive" on my computer with the same client_secret.json and copy the token over. Prove it with a test upload that shows up on my Drive. 6. Script order: check free space (work in /var/tmp) → dumps → tar → encrypt → test-decrypt into gzip -t → upload → compare size on Drive → rotate (delete old archives only after a confirmed upload, match by archive name, never keep fewer than 7) → remove temp files → Telegram report. Use trap so any failure sends me "failed at step N". Telegram: my OpenClaw bot token from an env file with mode 600, chat = my Telegram ID. 7. Schedule: a systemd timer at 04:00 in my time zone (ask me which), not cron. After the first automatic run, check the real start time in the log. Add a watchdog: every 5 minutes check the last-success mark; if it is older than 26 hours, alert me at most every 30 minutes. 8. Verify: run it once by hand and show the log. Download the archive, decrypt it, restore files and databases into a test location (never over live data) and compare. Write RESTORE.md: where the archives are, how to decrypt, what is inside, how to rebuild the server. Before editing any config file, copy it with a date. No destructive commands. At the end report: script path, schedule, archive size, run time, and what the restore test proved.

Copy 2: your computer every day
Your computer picks up the fresh archive by itself once a day. Run this prompt in Claude Code on the computer that will keep the copies. On a Mac the schedule is set with launchd, on Windows with Task Scheduler.
Prompt B · daily copy to this computer
Set up a daily copy of my server backups to this computer. Show me the plan first and wait for my OK. Never print secrets in the chat. Delete nothing outside the backup folder. My server already makes a nightly encrypted backup (a .gpg archive) and uploads it to Google Drive. 1. ssh to my server and find out where the backup script keeps the archive. If it deletes the archive after upload, offer me two options and wait for my choice: a) take the archive from Google Drive with rclone, signed in with my own Google account; b) change the server script to keep the last 2 archives in /var/backups/server (mode 700), and take it over SSH. 2. Create a folder for the copies: ~/ServerBackups (Windows: %USERPROFILE%\ServerBackups). 3. Write a small script that: - downloads the newest archive, and skips it if the file is already here; - checks that the size matches the source; - keeps the last 7 archives and deletes older ones only in this folder; - writes a log next to the archives. 4. Schedule it once a day at 10:00: launchd on macOS, Task Scheduler on Windows. If the computer was asleep at that time, run it after wake-up. 5. On any error show me a system notification on this computer. 6. Run it once by hand and show me the log and the file list. The archives are encrypted. Don't try to open them and don't ask for the passphrase.

Connect Claude Code to the new server
Rent a new server with Ubuntu 24.04, for example on netcup. The provider sends you its IP address and root password. Before any migration, Claude Code must reach the new server by SSH key only. The prompt below sets this up step by step. It is the same setup you did for your first server, now with the short name new-server.
Prompt D · SSH key for the new server
Hi! I just got a new server. Its IP address: <IP of the new server> Help me connect to it with an SSH key, without a password. The short name (alias) must be new-server. Give me a step-by-step plan and walk me through it, keeping in mind: - I may already have an SSH key from my first server; reuse it if it exists; - ~/.ssh/config may already exist: add to it, never overwrite it; - the connection must work here in Claude Code and from any terminal on my computer with one short command: ssh new-server. The plan must cover: - Check whether I already have an SSH key in ~/.ssh/. - If not, generate a new ed25519 key and explain in plain words what the private key, the public key and the passphrase are. - Copy the public key to the server with ssh-copy-id, entering the root password once in my terminal. On Windows, where ssh-copy-id is missing, give me the equivalent command. - Add the alias to ~/.ssh/config: Host new-server, HostName, User root, IdentityFile. - Check that ssh new-server connects without a password, and that you can run ssh new-server hostname from here. - Basic hardening: turn off password login in /etc/ssh/sshd_config, with a second terminal kept open in case something goes wrong. Check the config with sshd -t before reloading. IMPORTANT: - Explain every step in simple words: what we do and why. - After each step wait for my confirmation before going on. - If I make a mistake, for example paste a command in the wrong place, correct it and explain what went wrong. - Never ask me to paste the root password or the private key into the chat. I type the password only in my terminal.

Restore or move to the new server
The same steps work when the old server died and when you simply move to another provider. Claude Code restores everything and finishes with a check table.
Prompt E · restore on the new server
Restore my server from an encrypted backup onto a NEW server. For anything about OpenClaw use the openclaw-docs skill; don't invent commands. Before each step that changes something, tell me what you will do. Never print secrets in the chat. The new server is reachable with: ssh new-server (key login is already set up). If it asks for a password, stop and tell me. I will tell you where the archive is (Google Drive, a file on this computer or a portable disk) and give you RESTORE.md if I have it. 1. Connect with ssh new-server. Check: Ubuntu 24.04, free disk space at least 3 times the archive size. 2. Put the archive on the new server: upload it from this computer with scp, or download it from Google Drive with rclone. Compare the size with the original. 3. Ask me to create /root/.backup-passphrase on the new server myself: I open a terminal, run ssh new-server and paste the passphrase from Google Password Manager. Mode 600. You never see it. 4. Decrypt with gpg and unpack into /root/restore, not over the system. 5. Read the manifest: OpenClaw version, plugin list, Node version, Docker containers. Install the same OpenClaw version, Node, and Docker if it was there. 6. Return files to their places: ~/.openclaw, project folders, .env files, ~/.google_workspace_mcp, systemd units. For every SQLite database use its hot copy from the dumps, not the raw file. Restore Postgres or MySQL dumps if present. Before overwriting any file, save a dated copy. 7. SSH and firewall settings go last: check the config with sshd -t and make sure ssh new-server still works before reloading. 8. Reinstall the OpenClaw plugins from the manifest list. 9. Make sure the Gateway on the old server is stopped: two servers with the same Telegram bot fight over messages. 10. Run openclaw doctor and start the Gateway. 11. Turn the nightly backup back on for this server: timer, watchdog, Telegram report. 12. Final check. Show me a table "check / result / proof", one row each: a. OpenClaw version equals the manifest; openclaw doctor has no errors; openclaw gateway status and openclaw health are OK. b. openclaw models status: the ChatGPT sign-in is usable. c. openclaw mcp doctor --probe: every MCP server from the old server connects, GoogleWorkspace included. d. openclaw automations list: the same scheduled jobs as before, with next run times. e. Every bot and project from the manifest runs: systemctl --failed is empty, Docker containers are up. f. Databases: row counts match the dumps; every SQLite file passes integrity_check. g. .env files and token files are in place with mode 600. h. Security: firewall on with the same rules as before, SSH password login off, Gateway listens only on 127.0.0.1, no new open ports. i. The time zone matches the old server. j. Nightly backup: the timer is in systemctl list-timers, one manual run uploaded, the Telegram report arrived. 13. Tell me what to check by hand in Telegram, and what failed or needs my decision. If I think the old server was hacked, after the restore help me change the Telegram bot token in @BotFather, the Gateway token and other keys, following the docs.
